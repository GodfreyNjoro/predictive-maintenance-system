# Predictive Maintenance System (PMS)

AI-powered Next.js + Prisma + PostgreSQL application for system failure prediction.
Deployed at https://systempms.abacusai.app.

## Auth
Seeded admin: username `john`, password `johndoe123`. Login accepts username OR email.

## Architecture (current)
- **Pipeline**: Upload → decompress (gz/zip/tar) → auto-detect format (JSON/CSV/syslog/Apache/Nginx/Windows) → ParsedLogEntry → DynamicFeatureVector → Isolation Forest → ExplainablePrediction → System Analysis UI.
- **Storage**: `STORAGE_MODE=local|s3` via `lib/storage.ts` (unified facade over `lib/s3.ts` and `lib/local-storage.ts`).
- **Explainable AI**: `lib/explainable-ai.ts` — 9 root-cause patterns, causal chain, confidence breakdown, temporal context, prioritized recommendations, feature importance.
- **Federated AI**: `lib/federated-learning.ts` — local training + DP noise + aggregation (UI simulation).
- **Pages**: `/dashboard`, `/upload`, `/system-analysis`, `/predictions`, `/federated`, `/metrics`, `/audit`.

### Phase 3 — DMV snapshot feeds (waitStats + ioStats) — DONE (2026-04-26)
Adds two cumulative-counter feeds with first-class restart detection.

**Cumulative-delta helper** — `lib/mappers/cumulative.ts` (NEW)
- `computeDelta(current, previous) → { delta, reset }` — per-counter rollback detection (`current < previous` ⇒ reset).
- `detectServerRestart(prevStartTime, currStartTime) → boolean` — per-snapshot reset detection from `sys.dm_os_sys_info.sqlserver_start_time`.
- `toIsoString(v)` utility.
- Pure (no IO, no Prisma) — reusable from a future edge-collector agent.

**Mappers**
- `lib/mappers/mssql/wait-stats.ts` — `waitStatsMapper`, source `MSSQL.WaitStats`.
  - Cursor: `{ lastSnapshotAt, serverStartTime, counters: { [wait_type]: { wait_ms, wait_count, signal_wait_ms } } }`.
  - First snapshot primes cursor + emits ZERO entries (`previousCursor === null` check).
  - On restart: emits one synthetic `MSSQL.WaitStats.ServerRestart` warning, treats all counters as deltas (previous = 0).
  - Idle wait allowlist (`IDLE_WAIT_TYPES`) — defence-in-depth re-filter on top of SQL `WHERE` clause filter (Paul Randal's list).
  - Top 20 by `delta_wait_ms` DESC. logLevel: `info` baseline; `warning` on contention waits with `delta_wait_ms > 60_000`; `critical` with `> 300_000`.
  - Contention class: CXPACKET/CXCONSUMER, PAGEIOLATCH_*, PAGELATCH_*, LCK_*, WRITELOG, ASYNC_NETWORK_IO, RESOURCE_SEMAPHORE*, THREADPOOL, SOS_SCHEDULER_YIELD.
  - `features`: `{ deltaWaitMs, deltaWaitCount, deltaSignalWaitMs, avgWaitMs }`.
- `lib/mappers/mssql/io-stats.ts` — `ioStatsMapper`, source `MSSQL.IoStats`.
  - Cursor: `{ lastSnapshotAt, serverStartTime, counters: { [database_id:file_id]: { num_reads, num_writes, io_stall_read_ms, io_stall_write_ms } } }`.
  - Same prime + restart pattern. Synthetic restart event = `MSSQL.IoStats.ServerRestart`.
  - Skip files where `delta_num_reads + delta_num_writes === 0`.
  - logLevel: `info` baseline; `warning` when `peak_avg_latency_ms > 50` AND `total_ops > 100`; `critical` when `> 200`.
  - `peak_avg_latency_ms = max(avg_read_latency_ms, avg_write_latency_ms)`.
  - `features`: `{ avgReadLatencyMs, avgWriteLatencyMs, deltaReads, deltaWrites, sizeOnDiskMb }`.

**Mapper registry** — `lib/mappers/mssql/index.ts`
- Registers `waitStats` and `ioStats`. Re-exports both mappers.

**Connector** — `lib/connectors/mssql.ts`
- Imports `WaitStatsCursor`, `WaitStatsCursorRow`, `WaitStatsRawRow`, `waitStatsMapper`, `IoStatsCursor`, `IoStatsCursorRow`, `IoStatsRawRow`, `ioStatsMapper`.
- `listFeeds()` now probes `VIEW SERVER STATE` via a cheap `SELECT TOP 1 wait_type FROM sys.dm_os_wait_stats` — `viewServerState` flag drives `available` for both feeds; `unavailableReason` points to bootstrap scripts.
- `pull()` adds `case "waitStats"` and `case "ioStats"`.
- `pullWaitStats(ds, cursor)` and `pullIoStats(ds, cursor)` — both run a single snapshot query (no row cap, `partial: false`).
- `parseWaitStatsCursor` / `parseIoStatsCursor` — defensive parsers; malformed cursor → first-snapshot priming on next pull.
- `WAIT_STATS_QUERY` joins `sys.dm_os_wait_stats` ⨯ `sys.dm_os_sys_info` for `sqlserver_start_time`. Pre-filters idle waits in WHERE clause + `wait_time_ms > 0`. `SYSUTCDATETIME()` injects `snapshot_time`.
- `IO_STATS_QUERY` joins `sys.dm_io_virtual_file_stats(NULL, NULL)` ⨯ `sys.master_files` ⨯ `sys.dm_os_sys_info`.

**Explainable AI** — `lib/explainable-ai.ts`
- Extended `RootCauseHypothesis.category` union with `"wait_contention"` and `"io_latency"`.
- New pattern **SQL Server Wait Contention** matches sources via `/wait.?stats/i`, fires on `warningRate*0.9 + severityScore*0.7 + patternScore*0.4 > 0.18`. Diagnostic steps cover CXPACKET → MAXDOP, PAGEIOLATCH_* → IO, LCK_* → blocking.

### Phase 9 — Adaptive Intelligence Engine — DONE (2026-04-28)

Level 3 approach: a purpose-built analysis engine on top of the LLM that learns the user's specific infrastructure over time. ALL analysis is strictly per-application — data from one application is NEVER mixed with another.

**Schema additions** (`prisma/schema.prisma`):
- `AnalysisReport` — stores every intelligence report per app: summary, rawResponse (JSON), logFingerprint (JSON with source distribution + severity counts), autoTags[], verdict enum (PENDING/CONFIRMED/FALSE_POSITIVE/PARTIAL), operatorNotes, hoursBack, logCount, createdAt. FK to Application.
- `BaselineMetric` — rolling mean/stddev per app × source × metric: metricName, mean, stddev, sampleCount, lastUpdatedAt. Unique on `[applicationId, sourceName, metricName]`.
- `PatternSignature` — auto-catalogued recurring failure signatures per app: description, category, affectedSources[], occurrenceCount, confidence (0-1), severityTrend, avgLeadTimeMinutes, relatedPatternIds[], operatorNotes, isActive, firstSeenAt, lastSeenAt. FK to Application.
- All three have `applicationId` FK with `onDelete: Cascade`.

**Service modules** (`lib/intelligence/`):
- `analysis-store.ts` — Save/retrieve/search analysis reports, auto-extract tags from LLM JSON, Jaccard similarity for log fingerprint matching, find similar past reports.
- `baseline-learning.ts` — Welford's online algorithm for rolling mean/stddev updates. `updateBaselines()` computes per-source metrics (errorRate, warningRate, criticalRate, avgLatencyMs, totalEvents) and upserts. `detectDeviations()` flags metrics >2σ from baseline (requires ≥5 samples).
- `pattern-library.ts` — Fuzzy matching via 60% token overlap (Jaccard on bigrams). Auto-categorization from keywords. `upsertPatterns()` merges new LLM-extracted patterns with existing ones (confidence grows with recurrence, decays for stale patterns). `getActivePatterns()` returns patterns sorted by confidence.
- `rag-pipeline.ts` — `buildRAGContext()` assembles enriched prompt section from: up to 5 similar past reports, known active patterns, current baseline deviations. Formats as structured text for LLM injection.

**API changes**:
- `POST /api/intelligence/analyze` — REWRITTEN: now requires `applicationId`. Pipeline: pull logs → compute baselines → detect deviations → build RAG context → inject into LLM prompt → save report → upsert patterns from response. Streams SSE.
- `GET /api/intelligence/history` — List reports for an app (paginated, 20/page).
- `GET /api/intelligence/history/[id]` — Single report detail with parsed JSON.
- `POST /api/intelligence/feedback` — Submit verdict (CONFIRMED/FALSE_POSITIVE) + notes on reports or patterns. Updates confidence accordingly.
- `GET /api/intelligence/knowledge` — Returns patterns + baselines + report stats for an app.

**UI** — `app/(authenticated)/intelligence/page.tsx` — FULLY REWRITTEN with 3 tabs:
- **Analyze** tab: app selector, time range, analyze button, streaming results with 6 collapsible sections.
- **History** tab: timeline of past analyses with verdict badges, click to expand full report, feedback buttons (✓ Confirmed / ✗ False Positive) + notes input.
- **System Knowledge** tab: pattern cards (confidence bar, occurrence count, severity trend, affected sources), baselines table with deviation indicators, feedback stats.

## Coding conventions
- All new code is **additive** — no existing pages/APIs/models change behaviour for file uploads.
- Multi-tenancy: every new table carries `organizationId String @default("default")`; queries filter on it (no-op for single-tenant).
- Secrets: ONLY `lib/datasource/secrets.ts` decrypts. Never log plaintext. Use `redactForLog` for audit entries.
- DB-agnostic by default: any feature touching DB ingestion goes through the connector registry, not direct DBMS calls.
